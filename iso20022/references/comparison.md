# Comparison

Resolve both sides explicitly: exact messages/namespaces, publication editions, or contextually scoped concepts. If the intended versions remain ambiguous, ask using the supplied candidate list.

Compare matching subjects rather than entire manuals:
- XML structure: roots, paths, types, sequence/choice, occurrences, facets and supplied dependencies.
- Business behavior: purpose, roles, conditions, flows and MDR rules.
- Codes: separately versioned publications, values, meanings and applicability.

Cite both sides for each substantive difference. A fact absent from retrieved excerpts is not necessarily absent from the source. Distinguish confirmed differences, unchanged inspected content, and unestablished differences.

Same-named types in different namespaces are distinct definitions until compared. A structural change does not automatically establish a changed business rule. A schema-only versus documentation-only comparison has asymmetric evidence and must say so.

Use a concise Markdown comparison table where helpful. Label explanatory Mermaid views as derived and retain the source basis. Do not infer migration compatibility or supply transformation code without separately scoped implementation work.
